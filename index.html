CASE 01 / RESPONSIBILITY

肥大化した注文システムを、役割ごとに分離

注文の生成、タイマー、UI更新、正誤判定などが1つのクラスに集中していました。変更しやすい構成を目指し、進行・表示・データ管理に責務を分離しました。

注文データSushiOrderData
進行・正誤判定CustomerOrderWithTimer
UI表示CustomerOrderView

寿司の種類は文字列比較からenumを中心とした比較へ変更。既存の投擲処理との境界で変換し、互換性を維持しました。寿司の受け渡しの入口を一本化し、正誤判定を注文管理側に集約することで二重判定を防ぎました。

CASE 02 / GAME FLOW

来店から注文開始までを、状態に沿って制御

座席ごとに使用状態を管理し、客の生成時に空席を割り当てます。NavMesh上を移動した後、座席に合わせて位置・向きを補正し、座席への到着時に注文と制限時間を開始しました。

席の予約・解放処理を一本化。移動中に客が破棄されても、席が使用中のまま残らないようにしました。

CASE 03 / LIFECYCLE & MEMORY

リトライ時の参照切れと、記録画像の増加に対応

シーンをまたいで保持するScoreManagerに、新しいシーンのUI参照をつなぎ直す処理を実装。振り返り用の画面キャプチャは保存枚数に上限を設けました。また、リストのClear()だけでは残ってしまうネイティブメモリに対し、使用後のTexture2Dを明示的にDestroy()する処理を追加しました。

シーン再読み込み後のUI参照を復旧し、古いフレームの破棄と明示的なメモリ解放を組み合わせました。
